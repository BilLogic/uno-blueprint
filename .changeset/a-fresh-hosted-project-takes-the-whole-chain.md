`supabase db push` onto a brand-new hosted Supabase project runs the whole migration chain again. A hosted project grants every new function and table to `anon` and `authenticated` by name, which a stock Postgres does not, and two migrations' proofs stopped there: `21000116000000` (the recreated RPCs kept anon's own grant) and `21000214000000` (a test insert met the cells trigger before row level security). Both are corrected in place: the CLI never re-runs a recorded version, so no database that applied either file will differ, and the edits matter only where the original raised and rolled back. A new migration takes `add_lane` and `create_phase` back from `anon`, which the same restore had left callable on hosted projects with those defaults, and asserts that `anon` can execute no authoring write. CI now replays the chain behind the hosted default privileges and fails when a proof skips the authenticated path.

Upgrading a deployment: apply the migration `21000308000000_anon_runs_no_authoring_write.sql` (`supabase db push`, or your usual migration step). It revokes two grants and moves no rows. It raises, naming the function, if `anon` can still execute any `SECURITY DEFINER` function in `public` that guards itself with `is_service_account()` — a deployment's own included; a definer read such as the deployment's `search_blueprint` is outside the rule as long as its body does not call `is_service_account()`. A project pushed with `revoke execute on functions from anon, public` as a workaround should restore that default first; see `docs/connectors/supabase/database.md` § A fresh hosted project.
